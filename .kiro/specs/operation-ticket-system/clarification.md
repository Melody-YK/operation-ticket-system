## Q1：移动端形态选择

**分类**：功能范围（Functional Scope）

**问题**：
PRD 中多处提到"PC端/移动端"发起建票、操作执行，但未明确说明移动端的具体形态。这会直接影响技术架构选型和前端实现方案。请问采用哪种移动端方案？

**提供的选项**：
- **A**：原生移动 App（iOS + Android 各一套，通过应用商店发布，支持离线能力更强）
- **B**：移动端响应式 Web（同一套代码自适应 PC/移动端，通过浏览器访问，无需安装）
- **C**：混合模式（核心操作功能用原生 App 实现，查询浏览类用 Web 页面）
- **D**：PWA（渐进式 Web 应用，Web 技术打包，可安装到桌面，支持部分离线能力）

**推荐**：选项 B - 移动端响应式 Web，技术成本低，维护简单，一套代码覆盖所有终端

**用户选择**：B（移动端响应式 Web）

**解决方案**：
- 确认全系统采用响应式 Web 架构，PC/移动端使用同一套代码
- 补充 NFR-C03：移动端适配要求（操作执行页面完整可用，触屏交互适配）
- 更新 US-001 故事描述，明确提及"同一套响应式Web系统"
- 后续所有涉及移动端的描述均按此方案对齐

**应用范围**：
- NFR 兼容性需求 → 新增 NFR-C03
- US-001 用户故事 → 更新描述

## Q2：并发审核冲突处理

**分类**：边角情况（Edge Cases）

**问题**：
操作票三级审核涉及多个审核人，PRD 未明确说明并发场景的处理方式。例如：同一审核级别的两个人同时打开同一张操作票并各自提交审核结果，系统应如何处理？

**提供的选项**：
- **A**：先到先得（谁先提交结果谁生效，后提交的提示"操作票状态已变更，请刷新"）
- **B**：先到先得+审核锁定（审核人打开页面即锁定操作票，其他人看到"XX正在审核"提示）
- **C**：最终覆盖（后提交的结果覆盖先提交的）
- **D**：所有审核人均需审核（同一级别的所有人均需审核通过才算通过）

**推荐**：选项 B - 先到先得+审核锁定，避免多人同时操作导致的混乱

**用户选择**：B（先到先得+审核锁定）

**解决方案**：
- 在 UC-003（审核操作票）的备选流程中补充并发锁定机制
- 增加业务规则：审核人打开审核页面时锁定操作票，其他人在锁定期间看到"XX正在审核"提示
- 锁定超时机制：若审核人打开页面后30分钟内无操作，自动释放锁定

**应用范围**：
- UC-003 审核操作票用例 → 新增备选流程 A3（并发锁定）
- 业务规则 → 新增 BR-006（审核锁定规则）

## Q3：角色互斥规则

**分类**：领域与数据（Domain & Data）

**问题**：
一个人是否可以同时担任操作人、监护人、批准人、发令人中的多个角色？这影响人员管理数据库设计（四表合一还是分表）和权限校验逻辑。

**提供的选项**：
- **A**：允许一人多角色，但同一张票中角色互斥（可以同时有操作人和监护人资质，但不能审核自己创建的操作票）
- **B**：严格角色互斥（一个人只能拥有一个角色，不同角色需要不同人员账号）
- **C**：完全灵活（一人可多角色，且在同一张票中也可兼任）

**推荐**：选项 A - 允许一人多角色，但同一张票中角色互斥，更灵活且避免自我审批

**用户选择**：B（严格角色互斥）

**解决方案**：
- 确认四类人员实体保持独立设计
- 数据模型中假设 A-002 已确认（严格互斥）
- 人员信息管理按四类角色分别维护

**应用范围**：
- data-model.md → 假设 A-002 已验证为 Yes

## Q6：音视频数据存储策略

**分类**：领域与数据（Domain & Data）

**问题**：
操作执行过程中需同步采集音视频、标示、设备状态转换数据，但未明确音视频数据的存储位置、保留时长和文件大小限制。这影响存储架构设计。

**提供的选项**：
- **A**：数据库BLOB存储 + 永久保留（所有音视频存入数据库，不设保留期限）
- **B**：对象存储（OSS/S3）+ 90天保留（音视频存入对象存储，90天后自动清理）
- **C**：对象存储 + 与操作票同生命周期（音视频随操作票归档后永久保留）
- **D**：本地文件服务器 + 30天短期保留

**推荐**：选项 B - 对象存储 + 90天保留，性价比高且易于扩展
**用户选择**：A（数据库BLOB存储 + 永久保留）

**解决方案**：
- 音视频数据以BLOB形式存储在数据库中
- 不设自动清理机制，随操作票永久保留
- 需关注数据库存储容量增长，建议定期监控

**应用范围**：
- data-model.md → 电子操作票实体中 media_url 字段可能需要调整为BLOB类型或保留URL引用+实际BLOB存储

## Q10：现场数据上传与断点续传技术方案不确定性

**分类**：技术实现（Technical Implementation）

**问题**：
US-007（操作执行与数据实时上传）和 US-008（数据断点续传）涉及音视频数据实时上传、网络中断恢复等复杂技术场景。INVEST 检查中这两项的 E（Estimable）均为未通过，因为技术方案复杂度导致工作量估算不确定性高。需要明确技术选型和实现策略。

**提供的选项**：
- **A**：分片上传 + 本地 IndexedDB 缓存（前端分片→上传→服务端重组；网络中断时缓存到 IndexedDB，恢复后续传）
- **B**：WebSocket 实时流 + 本地文件缓存（通过 WebSocket 建立长连接实时推流；中断时写入本地临时文件）
- **C**：第三方上传 SDK（如阿里云 OSS 分片上传 SDK，自带断点续传能力）
- **D**：简化方案——仅上传图片和结构化数据，不上传音视频流（降低复杂度）

**推荐**：选项 A - 分片上传 + IndexedDB 缓存，技术成熟且不依赖第三方服务
**用户选择**：A（分片上传 + IndexedDB 缓存）

**解决方案**：
- 前端将音视频文件切分为固定大小分片（如 1MB/片）
- 每片上传承诺唯一分片ID，服务端接收后标记完成
- 网络中断时，未上传分片保留在 IndexedDB 中
- 网络恢复后，查询服务端已收到分片列表，上传缺失分片
- 所有分片上传完成后，服务端重组文件并计算 MD5 校验
- 前端同时记录操作日志（操作项 + 时间戳 + 数据分片映射）

**应用范围**：
- US-007 → 补充技术方案描述，明确分片上传策略
- US-008 → 断点续传策略明确为分片级续传
- NFR-P03 → 数据上传延迟指标调整

## Q13：归档数据对外接口缺少验收条件

**分类**：功能范围（Functional Scope）

**问题**：
US-016（归档数据对外接口）缺少验收条件，导致 T（Testable）未通过。该故事是 V2.0 功能，但接口设计需要提前规划，避免后续重构。目前未明确接口的协议、认证方式、数据格式、查询能力等关键设计决策。

**提供的选项**：
- **A**：补充完整验收条件，预定义接口规范（RESTful API + JWT 认证 + JSON 格式 + 分页查询）
- **B**：仅定义接口原则（标准化、可扩展），具体规范留待 V2.0 迭代时细化
- **C**：直接跳过验收条件，V2.0 开发时按需求重新分析
- **D**：先输出接口规范草案，待 V2.0 启动时与用户确认

**推荐**：选项 A - 补充验收条件并预定义接口规范，确保设计一致性
**用户选择**：A（补充验收条件 + 预定义接口规范）

**解决方案**：
- **US-016 补充验收条件**：
  ```gherkin
  Scenario: 按票号查询归档数据
    Given 操作票已完成归档
    When 外部系统按票号调用查询接口
    Then 返回该操作票的全量归档数据
    And 返回格式为标准 JSON

  Scenario: 按时间范围查询
    Given 多张操作票已完成归档
    When 外部系统按时间范围查询
    Then 返回该时间范围内的归档操作票列表
    And 支持分页返回

  Scenario: 权限认证
    Given 外部系统未提供有效认证凭证
    When 调用查询接口
    Then 返回 401 未授权

  Scenario: 数据完整
    Given 外部系统成功查询归档数据
    Then 返回数据包含操作票全量信息（基础信息、操作内容、执行记录、影像附件等）
  ```
- 预定义接口规范：
  - 协议：RESTful API over HTTPS
  - 认证：JWT（JSON Web Token）
  - 数据格式：JSON
  - 查询能力：按票号、时间范围、状态、操作人
  - 分页：支持 page/limit 参数
  - 限流：单 IP 每分钟 100 次

**应用范围**：
- US-016 → 新增验收条件
- 对外接口设计规范 → 预定义约束条件
